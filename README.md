# Bronuz Admin · веб-панель платформы

Отдельное React + TypeScript + Vite приложение для **владельца платформы**, не владельца клуба. Подключено к отдельному admin backend, который обращается к основной платформе через подписанный внутренний API. Бизнес-данные в браузере не подменяются демо-данными.

Дизайн: [Figma, Admin](https://www.figma.com/design/6kuFGruTD954JqNru0mzzw/Computer-club?node-id=202-23120). Использованы локальные изображения/SVG из макета, Steel-палитра и адаптированные поля существующего owner frontend. Tailwind не используется.

## Работает

- Вход: во временном локальном режиме — почта/пароль; в обычном режиме — дополнительно TOTP или резервный код; регистрация только по приглашению; QR подключения 2FA и однократный показ резервных кодов; восстановление пароля.
- Сессия: access token только в памяти, refresh в HttpOnly SameSite cookie. После перезагрузки сессия восстанавливается. Токены не хранятся в localStorage.
- Категории: RU/UZ/EN, slug, рынок, единица брони, порядок, встроенные иконки / JPG и PNG до 2 МиБ, публикация, скрытие, архив.
- Игры: поиск, пагинация, название, синонимы, платформы, жанр, возраст, категории, обложка JPG/PNG до 5 МиБ, публикация, скрытие, архив.
- Команда: email-приглашения, роли PLATFORM_OWNER / MODERATOR, блокировка, отзыв приглашений. Последнего владельца защищает backend.
- Журнал: сотрудники/авторизация и каталог, изменения «было → стало».
- Проверка версии при сохранении. Обработка ошибок, пустых состояний, запрет действий без прав. Изменения каталога доступны только владельцу.

- Модерация `/review`: очереди и счётчики статусов, поиск по клубам/залам, рынок, сортировка; отправленный снимок с фотографиями, планами залов, тарифами, меню и правилами; история отправок, отметки проверки и замечания, возврат/одобрение с подтверждением. Доступно владельцу платформы и модератору.

Главная показывает фактическое количество категорий, игр и сотрудников. Занятость, выручка, подписки, реклама и пользователи ещё не подключены: в интерфейсе нет вымышленных показателей, соответствующие разделы недоступны. Динамические характеристики категорий и предложения/объединение игр из макета — отдельные будущие модули. Эта поставка переносит доступные сценарии макета, а не реализует весь бизнес платформы.

## Запуск

Нужны Node.js 26, npm и работающий [admin backend](https://github.com/Azizbek-Salimov/gamingclub-adminpanel-backend).

```sh
npm ci
npm run dev
```

Откройте http://localhost:5175. Vite проксирует `/api/operations` на http://localhost:8084. Изменить адрес backend: `ADMIN_PROXY_TARGET=http://127.0.0.1:8084 npm run dev`. Backend должен разрешать `ADMIN_ORIGIN=http://localhost:5175`; открывайте именно localhost, чтобы Origin совпадал.

Для основной конфигурации сначала запустите общую платформу 8081 из `../../3-owner/web` командой `npm run local`. Staff-сервис находится в соседнем `../backend-admin`: начальная настройка — `python3 scripts/init-local.py`, затем `docker compose up -d --build` по его README. Секреты генерируются в игнорируемом `.env`; `ADMIN_PLATFORM_SECRET` должен совпадать на серверах. Staff-БД отдельная, клубы и модерация читаются с общей платформы. Автономный 8085 используется только с профилем `standalone`. Если на машине уже есть прежний Compose-проект `booking-admin-local`, сначала прочитайте раздел о сохранении его базы в README backend; новый проект не переносит данные автоматически.

Первое приглашение создаётся **из папки backend-admin**, когда контейнеры запущены:

```sh
docker compose run --rm --no-deps -e ADMIN_BOOTSTRAP_EMAIL=your-address@example.com admin --server.port=0 --admin.bootstrap-only=true
```

Откройте Mailpit http://localhost:18026 и перейдите по ссылке из письма. Пароль задаёт сам владелец. Временный профиль backend `local` открывает панель по паролю; в обычном режиме владелец подключает приложение 2FA и сохраняет резервные коды. Паролей по умолчанию нет. Последующих сотрудников приглашает владелец в разделе «Команда и роли». Локальная почта перехватывается Mailpit; для настоящей доставки настройте SMTP в backend.

## Проверка

```sh
npm run build
npm run test:api
npm test
```

Обычный тест проверяет вход, адаптивность 390/768/1440 и локальные изображения. Полный сценарий меняет данные, поэтому выключен по умолчанию. Для **одноразового тестового стенда**, где первое приглашение отправлено `admin-web-qa@example.test` и ещё не принято:

```sh
ADMIN_E2E_LOCAL=1 npm test
```

Он проходит реальную регистрацию с действующей серверной политикой (локальный вход по паролю либо MFA), восстановление сессии, CRUD категории/игры, загрузку изображений и архив, журнал и logout. Тестовый аккаунт не предназначен для использования человеком; удаляйте одноразовые тестовые БД после проверки. Не запускайте этот сценарий на рабочей базе.

## Production сборка

`npm run build` создаёт `dist/`. Раздавайте SPA с fallback на index.html и проксируйте `/api/operations/` на admin backend **на том же origin**. Пример nginx — `deploy/nginx.conf`. В контейнерном варианте `docker build -t booking-admin-web .`; backend должен быть доступен по DNS `admin:8084` в общей Docker-сети. Настройте HTTPS и ADMIN_ORIGIN на фактический домен; Secure cookie backend по умолчанию включена. Публичный backend bridge не должен быть доступен извне.

Секрет HMAC и ключ шифрования существуют только на серверах. Фронтенду они не нужны. Реальный production-домен, TLS, SMTP и развёртывание в этой поставке не настраивались.

Формы приглашения и восстановления читают минимальную длину пароля из GET /api/operations/v1/auth/policy. По умолчанию требуется 12 символов; локальный backend-профиль local допускает 9. Во временном локальном режиме MFA отключена; форма сразу принимает сессию после проверки пароля и показывает соответствующую подпись. В обычном режиме MFA обязательна. Пользовательские пароли не входят в исходный код.

Telegram OTP для сотрудников запланирован по запросу владельца, но пока не подключён. Текущий локальный вход не отправляет сообщения Telegram. Чтобы вернуть MFA в локальном backend, задайте `ADMIN_LOCAL_PASSWORD_LOGIN=false` и пересоздайте контейнер admin. Прежние сессии без второго фактора перестанут работать.

Файлы: иконки JPG/PNG до 2 МиБ (сервер уменьшает до 512 × 512), обложки JPG/PNG до 5 МиБ (длинная сторона до 1600 px). Пропорции и прозрачность сохраняются, EXIF-ориентация учитывается. POST /game-images отделён от POST /category-icons; preview поддерживает PNG/JPEG. Nginx допускает multipart до 6 МиБ.

Полный UI на одноразовом стенде запускайте из backend-admin: JAVA_HOME=/opt/homebrew/opt/openjdk@25/libexec/openjdk.jdk/Contents/Home python3 scripts/e2e.py --platform-jar ../../3-owner/backend/target/booking-backend-0.1.0-SNAPSHOT.jar --web-directory ../web-admin. Скрипт генерирует большую PNG-иконку и JPG-обложку, временные аккаунты/БД/Mailpit и прокси; проверяет HTTP и браузер, затем останавливает только свои процессы/контейнеры.

## Клубы на проверке

Открывайте `/review` в работающей панели. Экран использует staff-сессию и реальные методы `club-submissions`, `counts`, `history`, `media`, `review`, `decision` через существующий прокси. Фотографии загружаются с Bearer и показываются через временные Blob URL.

Порядок: открыть заявку → просмотреть шесть разделов → поставить отметки / добавить замечания → **Сохранить проверку** → **Одобрить заявку**, **Вернуть на исправление** либо **Отклонить редакцию**. Одобрение требует шести сохранённых отметок без замечаний; возврат требует хотя бы одного сохранённого замечания. Решение относится к клубу со всеми выбранными залами; приём бронирований настраивается отдельно.

Изменения используют серверный ETag заявки. При 412 локальные отметки/замечания остаются на экране, дальнейшие изменения блокируются до перечитывания серверной версии. При потере ответа или 5xx повтор отправляет исходное тело, If-Match и Idempotency-Key. История позволяет открыть предыдущие заявки в режиме чтения.

В основной конфигурации staff API 8084 обращается к общей платформе 8081: заявки кабинета владельца появляются в этой же очереди. Пустое состояние после успешного запроса означает отсутствие заявок по выбранным фильтрам. Недоступность платформы показывается ошибкой. У автономного стенда 8085 своя база; его очередь независима.

Отказ относится к редакции и позволяет новую подачу с ответом владельца. Админка показывает ответ, прежнее решение и изменённые разделы снимка. Новая проверка начинается с 0/6; ответ не означает автоматического устранения замечаний. При отказе обновления прежняя одобренная версия сохраняется. Блокировка клуба — отдельное действие. Нужна общая платформа с V28.

Журнал действий содержит три источника: каталог, модерация, сотрудники/вход. Модерация поддерживает фильтры clubId/actorId, курсор, причину решения и переход к заявке; доступ к журналу — у PLATFORM_OWNER. Очередь обновляется при возврате и получении фокуса; при конфликте показывается актуальный статус без потери локальных отметок.

Контракт сервера и Postman: [MODERATION.md](../backend-admin/docs/MODERATION.md).
